# TASK-035: Fix recurring payments — слишком много ложных кандидатов после импорта

**Status:** 📝 Draft  
**Priority:** 🟠 High — ломает CJM первого сеанса, подрывает доверие к продукту  
**Type:** Algorithm Fix  
**Effort:** M (2–4 часа)

---

## 📋 ТЗ (Product Manager)

### Проблема пользователя

После импорта выписки алгоритм предлагает десятки "регулярных платежей", которые таковыми не являются. Пользователь видит список из 30–50 кандидатов, большинство из которых — случайные совпадения (похожие суммы в разные месяцы). Это:

1. Создаёт когнитивную перегрузку — пользователь не понимает что подтверждать
2. Подрывает доверие к AI-функциям продукта ("приложение не понимает мои финансы")
3. Засоряет `SafeToSpend` — если пользователь случайно подтверждает ложный платёж, он резервируется в бюджете

### Root Cause

Текущий алгоритм в [`store.ts detectRecurringPayments`](../../apps/web/src/features/finance/store.ts):

1. **`MIN_AMOUNT = 100₽`** — слишком низкий порог. Любые два платежа по 150₽ в разные месяцы (кофе, парковка, мелкие покупки) попадают в кандидаты.

2. **`MIN_MONTHS = 2`** — достаточно 2 совпадений за 6 месяцев. Это слишком мало — случайные совпадения проходят фильтр.

3. **Нет фильтрации по категории** — транзакции категорий `cafe`, `food`, `shopping` (нерегулярные по природе) попадают в кандидаты наравне с `home` (аренда, ЖКХ).

4. **Нет минимального количества транзакций в кластере** — кластер из 2 транзакций за 6 месяцев считается "регулярным".

5. **Нет дедупликации по похожим label** — "Яндекс Такси 450₽" и "Яндекс Такси 480₽" создают два отдельных кандидата.

### Решение

Ужесточить критерии отбора кандидатов:

| Параметр | Было | Стало | Обоснование |
|----------|------|-------|-------------|
| `MIN_AMOUNT` | 100₽ | 500₽ | Подписки от 299₽ (Яндекс Плюс) — оставляем, кофе 150₽ — убираем |
| `MIN_MONTHS` | 2 | 3 | Нужно минимум 3 месяца подряд для паттерна |
| Исключить категории | — | `cafe`, `food`, `shopping`, `entertainment` | Нерегулярные по природе |
| Минимум транзакций в кластере | 2 | 3 | Кластер из 2 — случайность |
| Максимум кандидатов | ∞ | 20 | Ограничить UI-нагрузку |
| Сортировка | по дате | по confidence desc, затем amount desc | Самые надёжные — первыми |

### Acceptance Criteria

1. **Given** выписка с 500+ транзакциями за 6 месяцев  
   **When** запускается `detectRecurringPayments`  
   **Then** возвращается не более 20 кандидатов

2. **Given** транзакция категории `cafe` (кофе 200₽ × 3 раза в месяц)  
   **When** запускается детекция  
   **Then** она НЕ попадает в кандидаты

3. **Given** транзакция "Аренда квартиры 35000₽" повторяется 4 месяца подряд  
   **When** запускается детекция  
   **Then** она попадает в кандидаты с `confidence='high'`

4. **Given** транзакция "Яндекс Плюс 299₽" повторяется 3 месяца подряд  
   **When** запускается детекция  
   **Then** она попадает в кандидаты (MIN_AMOUNT=500₽ не отсекает — WAIT: 299₽ < 500₽)

   > ⚠️ **УТОЧНЕНИЕ**: Яндекс Плюс 299₽ < 500₽ нового порога. Нужно специальное правило для известных подписок.
   > **Решение**: добавить whitelist известных подписочных сервисов с `MIN_AMOUNT_SUBSCRIPTION = 100₽`:
   > `яндекс плюс`, `netflix`, `spotify`, `apple`, `google play`, `vk музыка`, `okko`, `кинопоиск`

5. **Given** кластер из 2 транзакций за 6 месяцев  
   **When** запускается детекция  
   **Then** он НЕ попадает в кандидаты (нужно минимум 3)

6. **Given** список кандидатов  
   **When** отображается в UI  
   **Then** `high confidence` кандидаты идут первыми, затем `medium`, затем `low`
