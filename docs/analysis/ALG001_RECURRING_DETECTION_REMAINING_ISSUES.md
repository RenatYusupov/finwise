# ALG-001: Анализ оставшихся false positives после TASK-035

**Дата:** 2026-05-26  
**Аналитик:** finwise-analyst  
**Контекст:** TASK-035 реализована (MIN_AMOUNT=500, MIN_MONTHS=3, EXCLUDE_CATEGORIES, subscription whitelist), но пользователь наблюдает ложные кандидаты. Анализ оставшихся причин.

---

## Корневая причина (пропущена в TASK-035)

**ALGORITHM_SPEC.md ALG-001, Изменение 2** явно предписывает `descriptionSimilarity >= 0.5` как **первичный ключ кластеризации**. Текущий код полностью игнорирует описание транзакции — кластеризация идёт только по сумме (±15%) и дню (±7).

**Следствие:** две разные транзакции с суммами 1400₽ и 1550₽ (разница 10.7%) в дни 5, 8, 12 разных месяцев → образуют кластер → false positive. Описания у них совершенно разные («Бургер Кинг», «DNS Техника», «Wildberries»), но алгоритм их не проверяет.

---

## Валидация предложенных фиксов

### Фикс 1: consecutive months (gap ≤ 1) — ✅ с уточнением

- Устраняет: платежи в январе, апреле, июле (gap=2 мес.) как «ежемесячные»
- Граничный случай: страховка раз в 2 месяца (gap=1) → проходит ✓
- Граничный случай: квартальный платёж (налоги ИП, gap=2) → отсекается при gap≤1 ⚠️
- **Рекомендация:** использовать max gap ≤ 2 месяца (не ≤ 1), чтобы сохранить биежемесячные паттерны

### Фикс 2: other_exp в EXCLUDE_CATEGORIES — ✅ корректен

- ~30% транзакций после импорта = other_exp (слабая категоризация)
- Пример: кофейня 1500₽, ресторан 1450₽, доставка 1600₽ — все other_exp в разные месяцы → cluster → false positive
- После фикса: исключаются на этапе фильтрации кандидатов ✓
- Нет негативных побочных эффектов: other_exp по определению не регулярная категория

### Фикс 3: убрать day wrap — ❌ ПРОТИВОРЕЧИТ ALGORITHM_SPEC.md

- ALGORITHM_SPEC.md ALG-001 Изменение 3 явно: *«Math.min(dayDiff, 31-dayDiff) — это правильно, оставить»*
- Контрпример: аренда 28-го → в феврале ложится 1-го следующего месяца
  - dayDiff(28, 1) = 27 без wrap → кластер не сложится → пропустим реальный платёж
  - dayDiff(28, 1) = min(27, 4) = 4 с wrap → корректно объединяются ✓
- **Вывод:** убирать нельзя. Это создаст ложные отрицания для end-of-month платежей.

### Фикс 4: DAY_TOLERANCE 7→4 — ⚠️ адресует симптом, не причину

- Проблема: без description similarity tolerance=7 слишком permissive
- Зарплата приходит 5-го, но в праздники сдвигается на 3-е или 9-е → разброс 6 дней → tolerance=4 даст ложный негатив
- С description similarity как первичным ключом: tolerance=7 перестаёт быть проблемой (описания «Перевод зарплата» совпадают, случайные транзакции не совпадают)
- **Вывод:** снижать tolerance нецелесообразно. Нужно внедрить description similarity.

## Влияние на ALG-003 (SafeToSpend)

Уменьшение false positives → `reservedUpcoming` уменьшается → `remaining` растёт → `safeToday` точнее. Чистый положительный эффект. Нет риска регрессий в SafeToSpend при условии, что реальные recurring payments сохраняются в кластерах.

## Граничные случаи для тестирования после фикса

1. Аренда 35 000₽ и кредит 34 500₽ (разница 1.4%) → с description similarity НЕ должны сливаться в один кластер
2. Яндекс Плюс 299₽ (subscription whitelist) × 3 мес. → должен детектироваться
3. Рандомные платежи 1400–1600₽ с разными описаниями × 3 мес. → НЕ должны быть кластером
4. Аренда 28-го числа → в феврале 1-го → должна объединяться (wrap работает)
5. Квартальный платёж (янв, апр, июль) → при gap≤2 отсекается
