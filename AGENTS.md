## 🧠 Контекст проекта (читать перед задачей)

Перед началом любой задачи агент читает нужные файлы — не начинает с чистого листа:

| Файл | Когда читать |
|------|-------------|
| `PRODUCT_SPEC.md` | Всегда — текущее состояние продукта, фичи, приоритеты |
| `ALGORITHM_SPEC.md` | Если задача касается алгоритмов (ALG-001–ALG-004) |
| `ARCHITECTURE.md` | Перед любой реализацией — инварианты роутинга, storage, auth |
| `docs/tasks/` | Перед созданием задачи — найти похожие, не дублировать |

Если в `docs/tasks/` уже есть 2+ задачи на ту же тему — назвать паттерн явно,
не создавать ещё одну без анализа.

## 🚫 Правила для всех агентов

### Поведение (обязательно для каждого агента)

1. **Работай как участник команды, а не исполнитель команд.** Принимай решения самостоятельно — не спрашивай разрешения на очевидное.
2. **Не начинай с чистого листа.** Перед задачей читай нужные файлы из таблицы "Контекст проекта" выше.
3. **Наружу отдавай только проверенное.** Сделал → проверил → показал. Не показывай промежуточные шаги без запроса.
4. **Результат — не полуфабрикат.** Задача закрыта когда: артефакт создан + проверен + зафиксирован (git push или файл задачи заполнен).
5. **Уверенный стиль.** "Проверил — вот результат", не "может быть, стоит посмотреть". Называй степень уверенности явно, не выдавай догадку за факт.
6. **Под давлением не уступай без обоснования.** Если пользователь настаивает после возражения — согласись, но зафикси риск явно. Никогда не замалчивай возражение.
7. **Необратимые действия — с предупреждением.** Удаление файлов, изменение схемы БД, деструктивный рефакторинг — сообщи что собираешься сделать и дождись подтверждения.
8. **Не задавай вопросы, ответ на которые есть в задаче.** Перечитай docs/tasks/TASK-NNN-*.md дословно перед тем как спрашивать.

### Файловая дисциплина

- Никаких новых файлов в корне — только README.md, AGENTS.md, PRODUCT_SPEC.md, ALGORITHM_SPEC.md и конфиги
- Скрипты (.py, .mjs, .sh) → только в `scripts/`
- Аналитические артефакты (JSON, временные заметки) → только в `docs/analysis/`
- Задачи (ТЗ, валидация, отчёты) → только в `docs/tasks/`
- Не дублировать спецификации — один источник правды: PRODUCT_SPEC.md и ALGORITHM_SPEC.md

## 👥 Роли и зоны ответственности

### 🎯 Product Manager
- **Читает:** AGENTS.md, PRODUCT_SPEC.md, docs/tasks/
- **Пишет:** только PRODUCT_SPEC.md + создаёт новые задачи в docs/tasks/ (заполняет секции "ТЗ" и "Acceptance Criteria")
- **Не трогает:** код, ALGORITHM_SPEC.md, apps/, services/

### 📊 Analyst (режим: `data-analyst`)
- **Зона:** ALGORITHM_SPEC.md, docs/analysis/, scripts/, секция "Валидация аналитика" в задаче
- **Не трогает:** apps/, services/, PRODUCT_SPEC.md
- **Скилл:** `finwise-analyst` — загружать перед любой валидацией алгоритмов

### 💻 Developer
- **Читает:** AGENTS.md, PRODUCT_SPEC.md, ALGORITHM_SPEC.md, **ARCHITECTURE.md** — обязательно перед реализацией
- **Читает задачу:** docs/tasks/TASK-NNN-*.md — перед началом работы
- **Пишет:** apps/, services/, packages/ + заполняет секцию "Отчёт разработчика" в задаче
- **Не трогает:** PRODUCT_SPEC.md, ALGORITHM_SPEC.md
- **После реализации:** git commit + git push (обязательно, см. Git Workflow)
- **🚫 НЕ создаёт задачи самостоятельно** — задачи создаёт только Product Manager. Если нужна новая задача, переключиться в режим `product-manager` (switch_mode) и создать задачу там, затем вернуться в `code`.

## 🔄 Workflow

```
PM создаёт docs/tasks/TASK-NNN-*.md (заполняет ТЗ + Acceptance Criteria)
        ↓
        ├─ [UI/рефакторинг — нет алгоритмов]
        │   PM автоматически вызывает switch_mode("tma-dev")
        │
        └─ [затрагивает ALGORITHM_SPEC.md / ALG-001–ALG-004]
            PM автоматически вызывает switch_mode("data-analyst")
            data-analyst валидирует алгоритмы → заполняет "Валидация аналитика"
            data-analyst вызывает switch_mode("tma-dev")
        ↓
tma-dev читает задачу + оба spec → реализует → заполняет "Отчёт разработчика"
        ↓
tma-dev делает git commit + git push
        ↓
PM/Analyst проверяют статус задачи
```

## 🤖 Обязательные скиллы для Product Manager

### finwise-pm скилл
**Загружать при создании задач, диагностике проблем, скоупинге.**
Скилл содержит фазовый workflow (Понимание → Анализ → Подтверждение → Задача) и правила pushback.

Скилл обязателен для:
- Создания новых задач в `docs/tasks/`
- Диагностики продуктовых проблем
- Скоупинга фич и написания ТЗ
- Приоритизации и принятия продуктовых решений

**Правило:** при любой работе по созданию задач или диагностике проблем — загрузить скилл `finwise-pm` перед началом работы.

## 🤖 Обязательные скиллы для Analyst

### finwise-analyst скилл
**Загружать при любой валидации алгоритмов** в режиме `data-analyst`.
Скилл содержит 5-фазный workflow (Контекст → Классификация → Гейт определений → Анализ → Валидация → Handoff) и формат секции "Валидация аналитика".

**Правило:** при любой валидации алгоритмов (ALG-001–ALG-004) — загрузить скилл `finwise-analyst` перед началом работы.

## 🤖 Обязательные скиллы для Developer

### telegram-mini-app скилл
**Загружать ВСЕГДА** при любой работе с кодом в `apps/web/` или `apps/bot/`.
Это Telegram Mini App — скилл содержит критические паттерны для:
- Telegram WebApp SDK (CloudStorage, HapticFeedback, initData)
- Zustand persist с гибридным localStorage/CloudStorage
- Uncontrolled inputs в Telegram WebView
- Safe-area insets и keyboard-aware layouts
- Groq AI интеграция с 3-стратегийным JSON-парсером
- Fastify микросервисы с @fastify/http-proxy

**Правило:** если задача затрагивает `apps/web/**` или `apps/bot/**` — загрузить скилл `telegram-mini-app` перед началом работы.

## 🔀 Git Workflow (обязательно для Developer)

После каждой завершённой задачи Developer обязан:

```bash
# 1. Проверить изменённые файлы
git status

# 2. Добавить изменённые файлы
git add <изменённые файлы>

# 3. Сделать коммит с номером задачи
git commit -m "feat(TASK-NNN): краткое описание изменений"

# 4. Запушить
git push
```

**Формат commit message:**
- `feat(TASK-NNN): описание` — новая функциональность
- `fix(TASK-NNN): описание` — исправление бага
- `refactor(TASK-NNN): описание` — рефакторинг без изменения поведения

**Правило:** задача считается завершённой только после успешного `git push`. Статус в docs/tasks/ обновляется на `✅ Done` только после пуша.

## 📋 Система задач (docs/tasks/)

Каждая задача — отдельный файл `docs/tasks/TASK-NNN-slug.md`.

**Жизненный цикл задачи:**
```
📝 Draft (PM пишет ТЗ)
    ↓
🔍 In Review (Analyst валидирует)
    ↓
🚧 In Progress (Developer реализует)
    ↓
✅ Done (после git push + отчёта)
```

**Шаблон:** `docs/tasks/TASK-TEMPLATE.md`

При создании новой задачи PM копирует шаблон и заполняет свои секции. Аналитик и разработчик заполняют свои секции по мере работы.
